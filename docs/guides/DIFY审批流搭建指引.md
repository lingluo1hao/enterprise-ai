# Dify 画布怎么画：采购单 AI 审批（点哪里、填什么）

> 面向：租户运营/实施，**不需要写代码**。照着点，20 分钟能跑通第一版。
> 前置：桥服务在跑（`http://192.168.200.1:8300`），该租户有 `kb-jm` / `kb-yh`；
> 演示单：jm `33`（小额，应自动批）/ `34`（大额，应转人工）；yh `35` / `36`。

---

## 0. 先建对应用类型

**工作室 → 创建空白应用 → 选「工作流（Workflow）」**。

不要选 Chatflow —— 审批是一次性任务（进一张单、出一条结论），不需要多轮对话。
选错了后面每个节点都要返工。

---

## 1. 建议分两版画，别一次画完

| 版本 | 节点 | 目的 |
|---|---|---|
| **v1 最小版** | 开始 → HTTP 请求 → 结束 | 只验证"能不能取到数"。**这一版不通，别往下画。** |
| **v2 完整版** | 开始 → HTTP → LLM → 条件分支 → 两个结束 | 加 AI 意见与自动/人工分流 |

下面按 v2 讲，但每一步都标了"v1 就该先验证"的点。

---

## 2. 逐节点操作

### 2.1 开始

点画布上默认的「开始」节点 → 右侧面板 → **添加输入字段**，加两个：

| 字段名 | 类型 | 必填 |
|---|---|---|
| `po_id` | 数字 | 是 |
| `knowledge_id` | 文本 | 是 |

### 2.2 HTTP 请求

画布空白处会出现一个 **「+」**（或节点右侧圆点拖出来）→ 选 **「HTTP 请求」** →
把「开始」节点右侧的小圆点**拖到**这个节点的左侧圆点（连线）。

右侧面板填：

| 位置 | 值 |
|---|---|
| 方法 | `POST` |
| URL | `http://192.168.200.1:8300/ai/pack` |
| Headers | `Authorization` = `Bearer dify-kb-local-2026`<br>`Content-Type` = `application/json` |
| Body → JSON | `{"po_id": {{#start.po_id#}}, "knowledge_id": "{{#start.knowledge_id#}}"}` |
| 超时 | `30` 秒（面板若没有就跳过） |

> **变量怎么插**：不要手打 `{{#...}}`。在 Body 输入框里点右侧的 **`{x}` 变量选择器**，
> 选「开始」→ `po_id`，它自己会填成正确语法。手打容易多空格，Dify 会当成普通字符串。

**★ v1 验证点**：现在右上角点 **「运行」**，填 `po_id=33`、`knowledge_id=kb-jm`。
运行完点开 HTTP 节点的「输出」，应该能看到：

```
body.ok = true
body.metrics.amount = 4940
body.gate.auto_eligible = true
body.route.nodes = [ ... 2 个 ... ]
```

**看不到 `body` 这一层**（只有一段字符串）→ 见 §4 排错第 4 条。

### 2.3 LLM

拖 **「LLM」** 节点，连到 HTTP 之后。

| 位置 | 值 |
|---|---|
| 模型 | `deepseek-chat`（或本地 `qwen2:5b`） |
| 温度 | `0` |
| SYSTEM | 见下（可直接粘） |
| USER | 用变量选择器选「HTTP 请求」→ `body` → `pack` → `material` |

SYSTEM 提示词（可改措辞，**不许改数据来源**）：

```
你是采购单审核助手。只能依据 user 内容里给出的数字和规则结论作答，
不得编造金额、库存、价格、供应商信息。
如果看到"信息不足"或缺失指标，必须在结论里点名缺了什么，
并给出"转人工"的建议，不得给出通过结论。
输出固定三行：
结论：建议通过 / 建议转人工 / 建议驳回
依据：<不超过三条，每条引用一个具体数字>
风险：<一句话>
```

### 2.4 条件分支

拖 **「条件分支」**，连到 LLM 之后。分支条件**引用 HTTP 节点**（不是 LLM）：

| 分支 | 条件 |
|---|---|
| IF | `{{#<HTTP节点>.body.gate.auto_eligible#}}` **是** `true` |
| ELSE | 其余 |

> 注意：Dify 的字段名可能是 `HTTP 请求` / `http_request` / `http-request-xxx`，
> 以变量选择器里看到的为准，**别照抄我写的节点名**。

### 2.5 两个结束节点

每个分支各拖一个 **「结束」** 节点，分别连到 IF / ELSE 分支的圆点。
**每个结束节点都要单独配输出变量**（这是新手最常漏的一步）：

| 输出变量名 | 类型 | 值 |
|---|---|---|
| `decision` | 文本 | IF 分支填 `自动通过`；ELSE 分支填 `转人工` |
| `opinion` | 文本 | 引用 LLM 的 `text` |
| `po_amount` | 数字 | 引用 HTTP 的 `body.metrics.amount` |
| `route_steps` | 数字 | 引用 HTTP 的 `body.route.nodes` 长度（取不到就省掉这行） |

## 3. 跑一遍验收

右上 **「运行」**：

| 输入 | 期望 |
|---|---|
| `po_id=33`, `knowledge_id=kb-jm` | `decision=自动通过`，金额 4940，路径 2 站 |
| `po_id=34`, `knowledge_id=kb-jm` | `decision=转人工`，金额 202800，路径 5 站 |
| `po_id=35`, `knowledge_id=kb-yh` | 能取到 yh 自己的单 |
| `po_id=35`, `knowledge_id=kb-jm` | **取数失败**（跨租户被拒），流程应报错中断 —— 这是对的 |

四条都符合，就可以右上 **「发布」**；发布后「访问 API」里能拿到应用 API Key，
业务系统就能直接调这个审批流。

## 4. 常见报错（按出现频率排序）

1. **变量选择器里看不到 `po_id`** —— 说明两个节点没连上。Dify 只列出**上游**节点的变量。
2. **HTTP 返回 401 / `error_code=1002`** —— `Authorization` 值多了引号或空格。
   正确是 `Bearer dify-kb-local-2026`（Bearer 后一个空格，**不要**加引号）。
3. **结束节点报「输出变量未定义」** —— 每个结束节点要**各自**配输出，不是配一个就共享。
4. **HTTP 输出只有一段字符串、取不到 `body.xxx`** —— 服务端返回头不是
   `application/json`，或面板里 Body/解析方式没选 JSON。解法：中间加一个
   **「代码执行」** 节点，`return {"data": json.loads(arg1)}`，后面引用 `data.xxx`。
5. **跑出来 `ok=false`，提示"采购单不存在"** —— 单号不属于该租户。
   jm 只认 33/34，yh 只认 35/36。
6. **LLM 编造数字** —— 温度没设 0，或 USER 里没有把 `material` 整个塞进去
   （只塞了部分字段）。只能给 material，不许自己拼。

## 5. 这套画的边界（别误会）

- **画布能改**：LLM 提示词、分支阈值、输出文案。
- **画布改不了**：取哪个租户（由 `knowledge_id` 白名单决定）、能不能自动批
  （最终由服务端 `Gate.decide()` 判，画布只是提前看个提示）。
- **社区版单 workspace**：同一个 Dify 里其他成员也能看到/改这条流程。
  命名请用 `jm-*` / `yh-*` 前缀，但这只是约定，不是隔离（见方案 §11）。

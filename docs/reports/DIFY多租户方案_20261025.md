# Dify 多租户自助编排方案

> 目标：**每个租户在自己的 Dify 里画流程（审批流），AI 自动审核，制度由平台兜底**。
> 本文是先给方案、再开发的依据。所有"实测"结论都可回源，命令写在 §2。

---

## 0. 一页结论

今天在这个环境里实测到**两条硬约束**，它们直接决定方案长什么样：

| # | 实测 | 影响 |
|---|---|---|
| 1 | `GET /console/api/system-features` → `deployment_edition: COMMUNITY` | 社区版**只有一个 workspace**，没有"多工作区"；所有成员共享同一份应用列表 |
| 2 | `POST /console/api/login` 明文口令 → `{"code":"authentication_failed","message":"Invalid encrypted data"}`，且 `/console/api/passport/public-key` = 404 | **服务端代登录（免登）这条路走不通**；SSO 要企业版 |

所以「每个租户自己画流程」不是加个页面就行，它本质是**隔离方案选型**。三条路，差别在隔离强度与成本，见 §4，**这一条需要你拍板**。

---

## 1. 大厂是怎么做的（对照参考）

| 产品 | 租户与编排隔离 | 审批流做法 | 对我们的启示 |
|---|---|---|---|
| Dify 云版 / 企业版 | 多 workspace，成员按 workspace 隔离 | 工作流画布 + HTTP/工具节点调业务系统 | **我们缺的就是"多 workspace"这一层** |
| 阿里百炼 | 业务空间（workspace）+ 应用/知识库绑定空间 | 流程编排 + 插件市场 | 空间是隔离的第一公民，应用必须挂在空间下 |
| Coze 扣子 | 团队空间 +  Bot 归属；发布到渠道 | 工作流 + 插件 + 触发器 | 租户自由度给到"编排层"，数据与权限不下放 |
| RAGFlow | 知识库级权限（团队/成员） | 无重编排，偏检索 | 检索侧按库隔离（我们已是 `kb-<tenant>`） |
| n8n | 项目（Project）+ 凭据隔离 | 任意流程 | 流程可自由画，但**凭据不归流程所有者** |

**共性**：**编排自由下放，数据与制度不下放。** 租户可以随便画流程，但"能不能批、批多少"必须由平台侧的规则引擎决定，不能由画布决定。这条是我们要照抄的核心。

## 3. 业务目标拆解

租户要能做四件事：**画流程 → 跑审批 → 看结果 → 改流程**。
平台要保证四件事：**隔离、制度兜底、审计、配额**。

对应到系统：

```
租户运营 ──> Dify 画布（画流程）
                 │  ① HTTP 节点 取数
                 ▼
        /ai/pack（数据 + 规则结论 + 材料）   ← 平台侧，制度在这里
                 │  ② 返回 gate.auto_eligible
                 ▼
        LLM 节点（按制度解释、生成意见）
                 │  ③ 条件分支：自动批 / 转人工 / 驳回
                 ▼
        回写业务系统 + 落审计（平台侧）
```

**关键设计**：③ 的分支条件看起来是租户画的，但**能不能自动批**由 `Gate.decide()` 说了算。租户把画布改成"一律走自动批"，服务端照样会拒 —— 这条已经在 `ai_approval.py` 里实现，方案里不改。

## 4. 三条路线（★ 需要拍板）

| | A · 单实例 + 应用前缀（现状） | B · 一租户一 Dify 实例 | C · 升级企业版 |
|---|---|---|---|
| 怎么隔离 | 应用名 `jm-*` / `yh-*`，知识库 `kb-<tenant>` | 每个租户一套 compose + 独立端口 | 多 workspace，成员按 workspace |
| **谁看不到谁** | ❌ 做不到（同 workspace 互相可见） | ✅ 物理隔离 | ✅ 逻辑隔离 |
| 租户能自己画 | ✅ 能，但能画到别人的应用 | ✅ 完全自由 | ✅ 完全自由 |
| 免登 | ❌ 手输 | ✅ 每实例独立账号，可做静态口令 | ✅ 企业版 OIDC |
| 成本 | 低（现在就能上） | 中：每租户 5 容器 / 约 2.5G 内存 | 高：License |
| 迁移成本 | — | 低（compose 复用，改端口 + 数据卷） | 中（导出导入应用） |
| 适用 | 内部 POC、单租户试点 | **多租户生产**（推荐） | 已有企业版 License 时 |

**我的建议（也是大厂常规做法）**：
- **P0 阶段用 A 做 POC**，跑通"租户画流程 + 制度兜底"这条业务闭环，验证价值；
- **P1 切 B**（一租户一实例）作为生产形态 —— 只有物理隔离才敢把画布交给租户；
- 若你们已有 Dify 企业版 License，直接走 C，B 的运维成本就省了。

> 说明：为什么不能"社区版单实例 + 靠制度约定不让租户乱看"—— 方案要能扛住一次"租户点了别人的应用"，一旦发生就是数据事故，靠约定不成立。

## 6. 审批流的标准画法（给租户的模板）

四段，租户只能在中间的 LLM 节点和分支阈值上改，**取数与判定不允许改**（HTTP 节点的 URL 由平台发布时写死）。

| 节点 | 谁配 | 内容 |
|---|---|---|
| 开始 | 平台 | 入参：单据号、租户、提交人 |
| HTTP 请求 | 平台（写死） | `POST /ai/pack`，body 带单据号；返回 `material` + `gate.auto_eligible` |
| LLM | **租户可改** | system 提示词写制度；user 用 `material`。只能改措辞，不能改数据来源 |
| 条件分支 | 租户可改阈值 | `gate.auto_eligible==true` → 自动批；否则 → 转人工 |
| 结束 | 平台 | 回写审批结果 + 审计 |

**模板下发方式**：把画布导出成 `templates/dify/approval_flow.json`，租户在 Dify 里「导入 DSL」直接用，改完发布。

**发布门禁**：发布前跑一次 `evalkit`（金标集），审批结论与人工标注的一致率低于阈值就不许发布。这一步在 `P2` 做。

## 10. 决策落定（2026-10-25）与实施步骤

**已定：走 C（企业版多 workspace）；免登不做。**

理由：我们是做企业智能系统的，租户自己画流程必须靠硬隔离；免登不是本次目标。
代码按 C 抽象，**当前社区版自动降级并如实标注，升级后只改配置不改代码**。

### 10.1 分期

|---|---|---|---|

### 10.3 P0 需要拍板的两个点

1. **P0 是否照上表做**（半天，只动上面两个文件，不动检索链路）；
2. **企业版大概什么时候到位** —— 决定 P1 是"马上"还是"先放着"。

## 11. 用户拍板后的落地口径（2026-10-25 16:40）

### 11.1 概念先对齐：应用 ≠ 实例

| | Dify **应用** | Dify **实例** |
|---|---|---|
| 是什么 | 一个 chatbot / workflow / agent | 一整套服务：web + api + worker + plugin_daemon + db + nginx |
| 数量关系 | 一个实例里可以建几十上百个应用 | 一台机器可以跑多个实例（各自端口 + 各自库） |
| 隔离效果 | **无**：社区版单 workspace，所有成员能看到并修改所有应用 | 强：不同实例之间完全看不到 |
| 资源 | 几乎不额外占 | 每套约 2–3G 内存 + 一个端口 + 一份数据库 |

所以"给每个租户建一个应用"**不叫隔离**，那是方案 A；"一租户一实例"是方案 B。

### 11.2 本轮决定：先不隔离，跑通业务（= 方案 A 的 P0）

- `config/dify_tenants.yaml` → `isolation: app_prefix`（页面显示「应用前缀隔离（当前生效）」，不再叫"降级"）；
- `/api/dify/tenants` 新增 `edition` 与 `effective_isolation`，由 `/console/api/system-features` 自动探测（缓存 5 分钟），实测返回 `COMMUNITY / app_prefix`；
- `/dify/enter/<t>` 按版本与配置出不同文案；跨租户 403 不变；
- 隔离欠账**记录在案**：一租户一实例（B）或企业版多工作区（C）二选一，等 license 与资源确认后再做。

### 11.3 业务闭环当前的唯一阻塞（实测）

`POST /ai/pack`（审批数字包）链路本身是通的，但**数据对不上租户**：

```
purchase_orders: 2 条   id=31 tenant=test_fac  /  id=32 tenant=default
dify_bridge 登记的知识库: kb-jm(tenant=jm) / kb-yh(tenant=yh) / kb-default(停用)
⇒ /ai/pack po_id=1|2 with kb-jm → 404「采购单 #N 不存在（tenant=jm）」
```

要跑通审批流，需要二选一：
1. 在 `jm` / `yh` 租户下各造 2 张**样例采购单**（`PO-DEMO-*`，含明细与库存），仅供演示；
2. 或新增 `kb-test_fac` 指向 `test_fac` 租户，用现有两张单演示（不改业务数据，但要放一个演示用知识库 ID）。

> 结论：**业务闭环卡在演示数据上，不在代码上。**

### 11.4 演示数据已造（2026-10-25 16:55）

用 `scripts/seed_demo_tenants.py` 给 jm / yh 各造一套（幂等，重复跑不重复插）：

| 租户 | 采购单 | id | 金额 | 期望审批路径 |
|---|---|---|---|---|
| jm | `PO-DEMO-JM-001` | 33 | 4,940.00 | 2 站，`auto_eligible=true` |
| jm | `PO-DEMO-JM-002` | 34 | 202,800.00 | 5 站，`auto_eligible=false` |
| yh | `PO-DEMO-YH-001` | 35 | 4,940.00 | 2 站 |
| yh | `PO-DEMO-YH-002` | 36 | 202,800.00 | 5 站 |

另含：仓库 `WH-DEMO`、供应商 `SUP-DEMO-A/B`、商品 `P-DEMO-1/2/3`（带成本价与安全库存）、库存 6 条。

**`/ai/pack` 端到端实测（HTTP 200）**：

```
po=33 kb=kb-jm → amount=4940    risk=high/140 route=2站 auto_eligible=true  material=965字
po=34 kb=kb-jm → amount=202800  risk=high/180 route=5站 auto_eligible=false material=2545字
```

⇒ **审批链路已跑通**：小额自动批、大额转人工、yh 独立取数（跨租户拿不到）。

所以风险被判 high —— 这是数据不足，不是规则错误。

画布怎么画见 `docs/guides/DIFY审批流搭建指引.md`（4 节点逐字段填写说明）。
